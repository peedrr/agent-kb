# Research: Proposal-document (RFC) formats whose primary consumer is an AI coding agent — recon landscape

Lane: recon-landscape. Depth: LIGHT (search-level coverage + 4 primary-source fetches). Scope: gap-fill only; Rust RFC template, PEP 1, Gerrit/Google/Malte-Ubl/PR-FAQ, RFC 2119/8174/BCP14, IESG 2025 keyword statement, idnits and agent-era ADR/SPEC evidence were EXCLUDED as prior art.
Date discipline: publication dates are asserted only where the source states them (page text, URL path, or file header). "Undated in source" = I did not observe a date and did not infer one.

## Summary
The proposal-format design space is not one space but three, distinguished by **revision lifecycle**, not by section list: (a) a mutable single working document updated in place during review (Rust RFC PR, Oxide RFD pre-publish, HashiCorp/Google Doc); (b) immutable numbered snapshots with expiry pressure (IETF Internet-Draft: `draft-name-NN`, 185-day expiry, tombstone on death); (c) an immutable record frozen at decision (published RFC, ADR, KEP `implemented`). Sections across all published templates converge hard on roughly problem/context → goals+non-goals → proposal → alternatives-including-do-nothing → risks/drawbacks → open questions → status — so the differentiating design choices for an agent-consumed proposal are lifecycle stance, machine-parseable status metadata, and where review disposition lives (in-document vs external tracker). The agent-era literature (2026) is real but thin and entirely about *authoring, pre-flighting and process-facilitating* proposals; **no one found has published a proposal format whose primary consumer is an agent**, and no agent-readable *review-response/disposition* schema was found. Sharp primary evidence for the last point exists only as tooling-side patterns (structured rubric output, emoji status in titles, `kep.yaml` metadata) rather than as a spec.

## Candidate sources
Labels: [direct] = source states it; [interpretation] = my reading. Confidence is per-source.

1. **RFC 7322, RFC Style Guide** — https://www.rfc-editor.org/rfc/rfc7322.html (Sept 2014; self-described "stable, infrequently updated" → freshness is a non-risk). [direct] Required ordered RFC skeleton (Abstract, Status of This Memo, TOC, Introduction, Requirements Language, IANA/Internationalization/Security Considerations, References, Acknowledgements, Contributors, Author's Address); order outside the body is *required*, inside the body *strongly recommended*. Proposal-relevant details: the Abstract "must not contain citations" and must be self-contained because it "will appear in isolation"; I-Ds may only be cited as informative references with version + "Work in Progress". Confidence: high.
2. **IETF Author Resources — "Required content" for Internet-Drafts** — https://authors.ietf.org/required-content (live/current). [direct] Verbatim mandatory boilerplate: "Internet-Drafts are draft documents valid for a maximum of six months and may be updated, replaced, or obsoleted…"; a mandatory exact expiry statement ("This Internet-Draft will expire on DD MMMM YYYY"); submissions missing required IPR boilerplate are rejected and the Secretariat will not add it. The boilerplate says *six months* while operative expiry is *185 days* (#3) — a documented mismatch. Confidence: high.
3. **Guidelines to Authors of Internet-Drafts (id-guidelines)** — https://ietf.github.io/id-guidelines/ (current revision of the older https://www.ietf.org/ietf-ftp/ietf/1id-guidelines.html). [direct] Expiry is exactly 185 days from posting; the clock restarts per version; the superseded version is removed from the repository; a "tombstone" retaining filename+version is created on expiry; being in "Publication Requested" suspends expiry but "AD is Watching" does not; expiry can be extended or the I-D resurrected by author/WG-chair/AD request. [interpretation] Closest existing analogue to "a proposal artifact with a built-in attention deadline", and the most transferable lifecycle idea in this lane. Confidence: high.
4. **IESG Last Call Guidance to the Community** — https://datatracker.ietf.org/doc/statement-iesg-last-call-guidance-to-the-community-20210416/ (2021-04-16; last-call mechanics predate it via RFC 2026/2418). [direct] Comments go to a dedicated list; subject lines must preserve the draft name so comments can be *automatically sorted*; purely editorial comments go only to authors/chairs/AD; directorate review teams route through the same list. Confidence: high.
5. **IESG Handling Ballot Positions** — https://datatracker.ietf.org/doc/statement-iesg-handling-ballot-positions-20220121/ (2022-01-21). [direct] Establishes the two-tier response taxonomy a proposal format must model: DISCUSS = *blocking* ("I cannot in good conscience send this document forward…"), must be explicitly replied to and tracked to clearance; COMMENT = non-blocking but authors are still expected to reply so the AD can see it was "seen and addressed". Acceptable resolutions explicitly include "not relevant for reasons A, B, C", "out of scope", and "we discussed this and decided against". Confidence: high.
6. **IETF "Document lifecycle" (Chairs Resources)** — https://chairs.ietf.org/en/documents/lifecycle (live, undated). [direct] Names gates and durations: AD evaluation 1–3 weeks, IETF Last Call 2–3 weeks (longer if it overlaps a meeting), IESG evaluation 2–3 weeks, plus rounds to clear DISCUSS/COMMENT; *major* changes require a new Last Call. Confidence: medium-high (durations are practice guidance, not rules).
7. **Oxide RFD 1 "Requests for Discussion"** — https://rfd.shared.oxide.computer/rfd/0001 (process doc; live index https://rfd.shared.oxide.computer/ shows 14 `discussion`, 63 `published`). [direct] Six states: `prediscussion`, `ideation`, `discussion`, `published`, `committed`, `abandoned`; per-document AsciiDoc metadata block (authors/state/discussion/labels) so state lives *in the artifact*; 3–5 business days comment guideline and "RFDs shouldn't be merged if no one else has read or commented on it"; a bot opens the PR and rewrites title/state/discussion URL; **discussion explicitly continues after `published`**; a `committed` RFD documents how a system works rather than freezing a decision. [interpretation] The strongest published counterexample to "freeze at decision". Confidence: high.
8. **Kubernetes Enhancement Proposal (KEP) process** — https://github.com/kubernetes/enhancements/blob/master/keps/sig-architecture/0000-kep-process/README.md (undated; references releases through 1.x). [direct] Seven statuses: `provisional`, `implementable`, `implemented`, `deferred`, `rejected`, `withdrawn`, `replaced` (+ `superseded-by`); `rejected` KEPs are **kept as historical documents**; KEP sections "can be merged into source control incrementally to support an iterative development process"; required `reviewers` and `approvers` metadata, distinct from authors; `implemented` = "no longer actively changed". Confidence: high.
9. **KEP template + `kep.yaml`** — https://github.com/kubernetes/enhancements/tree/master/keps/NNNN-kep-template (undated). [direct] Machine-readable YAML front-matter (`title`, `status`, `creation-date`, `reviewers`, `approvers`, `stage`, `latest-milestone`, `milestone.{alpha,beta,stable}`, `feature-gates`, `metrics`) alongside prose README — a **dual-representation** proposal: human prose + tooling metadata. Sections: Summary, Motivation, Goals, Non-Goals, Proposal, Risks and Mitigations, Design Details, Test Plan, Graduation Criteria, Upgrade/Downgrade, Version Skew, Production Readiness Review Questionnaire. Confidence: high.
10. **Kubernetes Production Readiness Review process** — https://github.com/kubernetes/community/blob/master/sig-architecture/production-readiness.md (undated; "as of 1.21, PRRs are now blocking"; Product Readiness Freeze added 1.23). [direct] PRR approval is a *blocking* gate; some questionnaire answers must appear in **both** README.md and `kep.yaml` "in order to support automated checks"; enforced by `kepval` / enhancements CI. [interpretation] Clearest precedent for proposal content deliberately duplicated into a machine-checkable field. Confidence: high.
11. **HashiCorp RFC template** — https://www.hashicorp.com/en/how-hashicorp-works/articles/rfc-template (undated). [direct] Overview → Background → Proposal/Goal, then freeform Heading-2 sections with recommended Implementation and UI/UX; explicit rule that abandoned ideas be **kept and marked abandoned with the reason** rather than deleted; explicit reader-exit design goal ("designed for readers to exit at any time"); prescriptive style rules. Confidence: high.
12. **HashiCorp writing practices / PRD template** — https://www.hashicorp.com/en/how-hashicorp-works/articles/writing-practices-and-culture (undated). [direct] PRD-then-RFC split (PRD = problem, RFC = solution); RFC needs explicit approval only from the appropriate team leads; company-wide email distribution for major projects; "our documents are the artifact, not the full process itself"; warns against over-detailing (background "a paragraph or two", proposal "one [paragraph]"). [interpretation] A published two-document pipeline where the proposal format is scoped to exclude problem definition. Confidence: medium-high.
13. **Rust RFC README (process, incl. FCP)** — https://github.com/rust-lang/rfcs/blob/master/README.md (undated/current). [direct] Motion to FCP carries a *disposition* (merge/close/**postpone**); requires "no strong consensus against"; FCP lasts 10 calendar days (≥5 business days) and is advertised (e.g. This Week in Rust); FCP can be cancelled, returning the RFC to development; a summary comment laying out "the current state of the discussion and major tradeoffs" usually precedes the motion; decisions get a rationale comment if not clear from the thread. Confidence: high.
14. **rust-lang/rfcbot-rs** — https://github.com/rust-lang/rfcbot-rs (undated). [direct] FCP is implemented as *machine-readable commands in review threads*: `@rfcbot fcp merge|close|postpone`, `reviewed`, `concern NAME`, `resolved NAME`. Structural properties worth copying: exactly one concern per comment; **only the original raiser can resolve their own concern**; a one-week-passed reminder comment; cancelling an FCP deletes concern records while the comments remain. Confidence: high.
15. **Rust language design team — "FCP decisions"** — https://lang-team.rust-lang.org/fcp-decisions.html (undated; reflects the post-2019 rfcbot threshold change). [direct] FCP reversal requires *another* FCP and "some change in circumstances"; if a resolution FCP changed the proposal, **the original FCP is restarted**; FCP entry no longer requires unanimous sign-off (majority + no registered concern + <3 approvals outstanding). Confidence: high.
16. **Rust Internals — "PSA: tweaks to FCP process"** — https://internals.rust-lang.org/t/psa-tweaks-to-fcp-process/6775 (undated in snippet). [direct] Documents the tradeoff: unanimity left items "in limbo", but the relaxed rule creates a race where the first approvals start the clock before later members see the motion; a time-delay compromise was proposed; maintainer agreed stabilization should keep a higher bar. [interpretation] Best published evidence on *failure modes* of quorum+timeout deliberation. Confidence: medium-high (forum thread, primary by participants).
17. **W3C DisCo (Disposition of Comments generator)** — https://www.w3.org/2006/07/SWD/RDFa/disco (2006 path; tool page). [direct] DoC generated from per-issue annotations with a fixed field vocabulary: `ACTION: Accept|Reject`, `CHANGE-TYPE: None|Editorial|Substantive`, `RESOLUTION: <text>`, `COMMENTER-RESPONSE: Accept|Reject`; issue titles need a common prefix so a review round can be selected ("Last Call Comment: …"). Confidence: high. Freshness: mechanism is 2006-era but still the W3C pattern; W3C material here is stale.
18. **W3C CSSWG `issuegen.pl` DoC field set** — https://github.com/w3c/csswg-drafts/blob/main/bin/issuegen.pl (undated, live). [direct] Fields: Summary, From, Comment (URL to the message), Response (URL to the editor's resolution), Changes (diff links), `Closed:` status (Accepted / OutOfScope / Invalid / Rejected / Retracted), `Verified:` (URL where the *commenter* confirms satisfaction), `Resolved:` (the *authority* for closure: Editorial / Bugfix / WG-resolution URL / Editor discretion). Advisory: silence is consent after ~2 weeks; seek the commenter's verification because they spot mistakes. [interpretation] Most complete published schema found for a post-review artifact — and it is human-oriented; no agent-facing equivalent exists. Confidence: high.
19. **Squarespace — "The Power of 'Yes, if'"** — https://engineering.squarespace.com/blog/2019/the-power-of-yes-if (2019). [direct] Approver sign-off table where votes are **"yes" or "not yet"** (deliberately no "no"), plus a free-text `Status` field the author uses to *state what kind of review is wanted at this stage*; sections include Alternatives Considered / Prior Art, Dependencies, Operational work; a recurring Council plus a twice-weekly deep Architecture Review. Confidence: high.
20. **Spotify (Heroic) RFC process** — https://github.com/spotify/heroic/blob/master/rfcs.md (undated). [direct] Minimal template: Problem / Suggestion / Related issues; lifecycle as GitHub labels `rfc:draft` → `note:accepted` / `note:wontfix`; "discussion around the RFC and proposed solution should live in the RFC and not the linked issues"; rejected RFCs are closed out and retained. [interpretation] The *minimum viable* proposal body is three sections when review structure carries the rest. Confidence: medium-high.
21. **Spotify engineering — ADR guidance (RFC→ADR pipeline)** — https://engineering.atspotify.com/2020/04/when-should-i-write-an-architecture-decision-record (2020-04). [direct] Explicit decision tree: problem + no blessed solution + big change → write an RFC; RFC concluded with a solution → write an ADR. [interpretation] Published statement of the proposal→record handoff. Confidence: medium-high (blog framing, not policy).
22. **Uber H3 RFC template** — https://github.com/uber/h3/blob/master/dev-docs/RFCs/rfc-template.md (undated). [direct] Header is only Authors / Date / Status: Draft. Confidence: medium (low signal; product-repo template, not company process).
23. **Pragmatic Engineer — "Engineering Planning with RFCs, Design Documents and ADRs"** — https://newsletter.pragmaticengineer.com/p/rfcs-and-design-docs (undated in snippet). [direct] Uber's pre-RFC artifact was "DUCK" (a document that *rubber-ducked* thinking, describing proposals/problems in simple language); DUCK → RFC → added `approver` fields → a tiered planning process with lightweight templates for team-scoped changes and heavyweight templates for org-wide, plus tooling tracking approvers as tasks. [interpretation] Best published evidence that **tiering by blast radius** is the mature end-state. Confidence: medium (secondhand w.r.t. Uber internals).
24. **philcalcado.com — "Writing AI-Assisted RFCs"** — https://philcalcado.com/2026/07/10/writing_ai_assisted_rfcs.html (2026-07-10; RECENT — the single most on-topic scope-4 source found). [direct] The author of the Structured RFC Process revisits it for the LLM era: the process is *change management*, not the document; "the part I had to change is the part I always said mattered least: the format". Concrete format decisions: accountability ("I don't care who typed the words, you own them" — disclosure of AI authorship is now *less* useful than defensible ownership); keep NABC; **always include "Do Nothing" as an alternative**; the argument must be narrative prose not bullets, because LLMs convert bullets into plausible prose without the missing reasoning; **implementation detail (filenames, signatures, DDL, migration sequencing) is out of scope** — the LLM-with-repo-access failure mode is "architectural proposal [that] comes back with class names, schemas, method signatures"; diagrams become first-class *because* LLMs are currently worse at them than at prose (forcing the author back into the loop); claims must be traceable so a reviewer can "give the RFC and its sources to an LLM and ask it to check whether the sources actually support the claims"; a **word budget** (2,500 hard / 1,500–2,000 target) on the core proposal; and a **rubric used as an agent pre-flight** — "hand the document and the rubric to an LLM and tell it to be annoying: find claims with no evidence, find alternatives that are obviously straw men, find bullets pretending to be reasoning, tell me where I'm explaining implementation instead of the proposal, check the word count" — explicitly "not a grading system… it means the document is ready for humans to have the argument". The RFC itself is deliberately kept in an "eternal Feedback Requested" state **with a revisit date**. Confidence: high (primary; author's own process).
25. **philcalcado.com — "A Structured RFC Process"** — https://philcalcado.com/2018/11/19/a_structured_rfc_process.html (2018-11-19; the original process being reformatted). [direct, via #24's summary — page not fetched this pass] RFCs **expire** and carry a revisit date; the author names who has the final say vs who is only giving feedback; every piece of feedback gets a good-faith response even when rejected; the review meeting is a milestone rather than the venue. Confidence: high (author's own restatement; unfetched).
26. **marzouk.io — "AI as Process Infrastructure: Practical Learnings from an AI-augmented RFC Process"** — https://marzouk.io/posts/ai-rfc (undated in source; describes a live deployment and cites a 2025 arXiv paper → 2025–2026). [direct] Reported org experience: ~60% of ~20 RFCs in nine months sat open with no updates for >6 weeks; a daily LLM coordinator read Confluence RFCs + comments and answered fixed questions (progress vs stated milestones; unaddressed comments; pending action items; whether status should change; all questions answered but reviewers never signed off; document-structure and discussion-health quality; escalation flag), driving Slack reminders and a dashboard; backlog cleared in 4 weeks with only two deadline extensions since. Format advice stated: define a staged workflow; use a **simple, semi-structured format** — a leading table with reviewers and milestone dates so the extractor "can easily extract the data it needs… without risk of hallucination"; **emoji in titles to encode state**; give explicit quality *criteria and examples* rather than "evaluate quality"; deliberately **keep the AI out of content generation and comment answering**. Confidence: medium-high (single-org, self-reported metrics; the *format* advice is the durable part).
27. **eric.lubow.org — "Implementing an RFC Process That Engineers Don't Hate"** — https://eric.lubow.org/2026/implementing-an-rfc-process-that-engineers-dont-hate/ (2026 URL path; page asset dated 2025-12). [direct] A functional template needs only five things: the problem, the proposed solution, the why, the discarded alternatives, and the risks; "if it takes longer to document the change than it would to code it, you're over-indexing on detail"; the proposing team **owns the decision** (the meeting is "a sounding board… not an approval committee"); three post-review outcomes — Validated Alignment / Constructive Course Correction / **Documented "No"** — and rejected RFCs must be kept because "a rejected RFC is still valuable as it documents why we decided not to do something, which prevents the same proposal from coming back six months later without new information"; names "the trap of the silent RFC" as the main failure mode. Confidence: medium-high (practitioner blog, no metrics).
28. **ohadravid.github.io — "Let Them Write RFCs"** — https://ohadravid.github.io/posts/2026-08-let-them-write-rfcs/ (2026-08-11; RECENT). [direct] An agent-heavy solo workflow: have the model emit `$PROBLEM_RFC.md` **before** code and iterate V1/V2/… ("hundreds of millions of tokens to write four versions of the same markdown file"), because an RFC optimizes the model for *understanding and explanation* whereas plan mode beelines to the nearest solution. Four questions the RFC must answer: what exactly is the problem; how bad or important; will this solution fix it; how costly vs the alternatives. Explicitly distinguishes an RFC from a plan ("the details are everything" in a plan) and says the structure "should be flexible enough to fit the problem", sometimes borrowing Rust's RFC style. [interpretation] Strongest evidence that an agent-first proposal format's justification is comprehension/falsification, not implementation handoff. Confidence: high (primary, first-person).

## Per-scope-section: settled / contested / DEEP
### 1. IETF proposal-document machinery
- **Settled [direct]:** I-D and RFC are different artifact classes with different contracts. I-D = temporary, expiring (185 days), versioned, citable only as informative "Work in Progress"; RFC = permanent, ordered, with editor-supplied boilerplate, immutable once published. RFC 7322 fixes the *post-decision* skeleton; the I-D is the actual *proposal* carrier and its only hard requirements are boilerplate, expiry date, and stream/status.
- **Settled:** the I-D mechanism is the only widely-used proposal artifact with **automatic death by default** (expiry + tombstone) plus per-version frozen snapshots.
- **Contested:** whether a *proposal* should carry the RFC's heavy required sections. In practice the RFC skeleton is a publication contract, not a deliberation contract — IETF deliberation content (comment resolution, DISCUSS/COMMENT disposition) lives outside the document.
- **DEEP flag: YES.** "Revision identity + expiry semantics as design primitives" (versioned immutable snapshots vs editable working copy; tombstone/abandonment records; expiry pressure on reviewer behaviour). Targets: id-guidelines, RFC 7322 §4, the I-D tracker state machine.

### 2. Other published RFC/design-proposal templates
- **Settled [direct]:** section lists converge. Across Oxide RFD, KEP, HashiCorp, and minimal sets (Spotify Heroic; Uber H3), the invariant core is **problem → goals & non-goals → proposal → alternatives incl. do-nothing → risks/drawbacks → open items**. Two published templates mandate a Drawbacks/risks section, and Rust RFC places Drawbacks **before** Rationale and Alternatives.
- **Settled:** machine-readable status metadata in the artifact is already mainstream in the two most process-heavy systems (KEP `kep.yaml`; Oxide metadata block); Oxide's bot *rewrites* the artifact's state field; KEPs duplicate PRR answers in README + YAML specifically for automated checks.
- **Settled:** tiering by blast radius is the mature pattern (Uber lightweight vs heavyweight; Squarespace RFC vs Council; SIG-scoped vs cross-cutting KEPs).
- **Contested:** whether the proposal must include problem definition or whether it belongs in a *preceding* document (HashiCorp PRD→RFC; philcalcado NABC keeps it in one; Uber DUCK→RFC split it).
- **Gaps:** no verified company-wide Spotify/Google/Meta RFC template — only product-repo templates and blog reproductions. Prior art already covers Google design docs (Malte Ubl).
- **DEEP flag: YES (narrow).** "What KEP's `kep.yaml` + Oxide's metadata block + Kubernetes PRR duplication reveal about designing a machine-checkable proposal header." Targets: KEP process doc, KEP template, PRR process doc. Non-overlapping with prior art.

### 3. Deliberation machinery
- **Settled [direct]:** mature systems separate four things a naive format conflates — (a) proposal text, (b) review thread, (c) *disposition* of each comment (accept/reject/defer/out-of-scope), (d) decision rationale. Instantiated by Rust (rfcbot commands + FCP disposition + rationale comment), IETF (DISCUSS/COMMENT + Last Call + ballot positions), W3C (DisCo/issuegen vocabulary), Kubernetes (`approvers` + PRR gate), Squarespace (yes / "yes, if" / "not yet").
- **Settled:** a **time-boxed, advertised final-comment window with an explicit cancel path** is the standard anti-stall mechanism (Rust FCP 10 days, advertised, cancellable, restart-on-change; IETF Last Call 2–3 weeks; Oxide 3–5 business days; W3C 2-week silence-is-consent; Kubernetes freezes).
- **Settled:** two-tier feedback semantics recur independently — blocking vs non-blocking, with blocking items requiring explicit resolution *by the raiser* (IETF DISCUSS; rfcbot concern resolvable only by its author; Squarespace "not yet") and non-blocking items requiring only a visible response.
- **Contested:** quorum rules for *starting* the clock. Rust moved from unanimity to majority+no-concern+<3 outstanding and documented the resulting race (source 16). No published system resolves "some reviewers haven't seen it yet" except by time delay.
- **Contested (mild):** whether rejected/deferred proposals are retained. All strong published positions say keep (Oxide `abandoned`, KEP `rejected`, Spotify `note:wontfix`, eric.lubow "Documented No"); no serious published advocate for deletion was found.
- **Gap:** no published, reusable **disposition-of-comments schema intended for machine consumption**. W3C's is closest and is a 2006-era XSLT/annotation convention gated on human-written notes. KEP's `kepval`-checkable fields are the closest machine-checked analogue but cover PRR answers, not comment disposition.
- **DEEP flag: YES — highest priority.** "How proposals record and resolve review feedback; does an agent-consumable disposition-of-comments format exist?" Targets: rfcbot-rs command grammar + concern lifecycle, the four IESG statements, DisCo + CSSWG issuegen, KEP PRR tooling. Explicitly test the hypothesis that **no agent-readable DoC format exists**.

### 4. Agent-era (2025–2026) writing on proposals for agent consumption
- **Settled [direct]:** the topic exists but is small, and every source found concerns **authoring, pre-flighting, or process-facilitating** proposals — never a format designed for an agent as *primary reader*. Independent contributors found: philcalcado (2026-07-10), ohadravid (2026-08-11), marzouk (process coordinator), eric.lubow (2026).
- **Settled:** the specific agent-era format moves that recur across independent sources are (i) a short leading **structured metadata/header block** (reviewers, approvers, dates, status) a model can extract without hallucinating; (ii) **explicit enumerated quality criteria / rubric** handed to the model rather than "evaluate quality"; (iii) an **evidence trail on claims** so review can be machine-checked; (iv) keeping **implementation detail out** because repo-access agents over-concretize.
- **Settled (caution):** the dominant failure mode named independently by two sources is generated prose masking unchanged reasoning — "plausible prose without filling in the missing reasoning" and "the document can arrive first: five convincing pages before anyone has had a single serious thought" (both philcalcado); marzouk and eric.lubow report stalling/silence *after* publication. So the format's job is arguably falsification aid + stall detector, not completeness.
- **Contested:** whether AI authorship should be *disclosed* in the proposal. philcalcado argues disclosure is becoming *less* useful than accountable ownership — cutting against the provenance/"nutrition label" trend. Genuine open design question.
- **Contested:** whether the agent participates in *content* or only *process*. marzouk deliberately scoped its coordinator out of content generation and comment answering; philcalcado uses a rubric pre-flight but keeps humans in the argument; the adversarial-review agent files (31) push agents into content critique with evidence gates. No source resolves this.
- **Missing entirely:** any proposal format specification defining an agent as consumer; any agent-readable review-response schema; any measured evaluation of proposal formats for agent comprehension (unlike the ADR/SPEC evaluation work in prior art).
- **DEEP flag: YES.** "Synthesize a defensible agent-era proposal format from (i) rubric-as-preflight, (ii) structured header for extraction, (iii) evidence traceability, (iv) implementation-detail exclusion, (v) explicit anti-plausible-prose countermeasures." Targets: the four sources in full, plus the agent-skill ecosystem (create-rfc-type skills) as the de facto standard by volume of use.

### 5. The proposal-vs-record distinction
- **Settled [direct]:** the split is drawn on **pre-decision vs post-decision**, canonically stated by Fowler ("proposed while it is under discussion… accepted once the team accepts it"; once accepted never reopened, supersede instead), Spotify (RFC concludes → write ADR), DesignDoc ("the document often changes significantly during review"), and eric.lubow (the RFC is a thinking tool; the meeting is not an approval committee).
- **Settled — content unique to the pre-decision artifact, observed in primary sources:** (a) open questions as live items with owners/dates (Rust "Unresolved questions"; Squarespace's free-text Status used to *request a specific kind of review*; create-rfc leaves `Outcome` an explicit placeholder); (b) alternatives as *live contenders* rather than rejected options — philcalcado makes "Do Nothing" mandatory precisely to keep the null hypothesis live; Squarespace adds "Alternatives Considered / Prior Art"; (c) explicit feedback solicitation with a named audience and deadline (Oxide 3–5 days; Rust FCP 10 days; IETF Last Call; Spotify public RFC "open until Friday, November 5"); (d) named deciders/reviewers distinct from authors (KEP `reviewers`/`approvers`; Squarespace Approvers table; Rust "who has the final say vs who is only giving feedback"); (e) authorship/AI provenance *if* it matters (contested, see §4); (f) the acknowledged incompleteness itself.
- **Settled — content unique to the post-decision record:** the decision statement and *who* decided; rationale/ballot positions (IESG ballot positions; Rust rationale comment; DISCUSS clearance); the disposition of every comment raised; consequences/drawbacks on the accepted option; supersession pointers (`superseded-by`, `Supersedes:`, `replaces`/`replaced`, `abandoned`).
- **Contested — the most decision-relevant disagreement for this format.**
  - **Freeze-at-decision camp [direct]:** Fowler/ADR ("once accepted, never reopened; supersede"), ADR immutability norms, KEP `implemented` = "no longer actively changed", published RFC = permanent.
  - **Living-after-publish camp [direct]:** Oxide retains the discussion link on `published` RFDs and permits continued discussion and infrequent changes to `committed` RFDs; philcalcado keeps an "eternal Feedback Requested" RFC with a **revisit date** and states "my RFCs expire: so we can disagree, commit, and revisit instead of stalling on getting it right the first time"; HashiCorp keeps abandoned ideas in-document rather than deleting.
  - **Hybrid (most common in practice):** the proposal is edited pre-merge and frozen at merge, then superseded rather than edited (Kubernetes `replaced`; Rust RFCs live as `text/NNNN-*.md`).
  [interpretation] Three independent published mechanisms — philcalcado's revisit date, Oxide's living `published` RFD, and the I-D's hard expiry — all encode *proposals are provisional until re-affirmed*. That is a strong, non-obvious design direction for an agent-consumed proposal, because an agent re-reading a stale proposal needs a machine-checkable staleness signal.
- **DEEP flag: YES.** "Proposal-vs-record content boundary, and staleness/revisit mechanics (expiry dates, revisit triggers, supersession pointers) as machine-readable fields." Targets: philcalcado 2018 + 2026 in full, Oxide RFD 1 + the rfd-api state machine, ADR/Fowler/MADR immutability, KEP status semantics.

## Contradictions
1. **Records are immutable after acceptance vs RFDs/RFCs stay editable after publication.** Fowler/ADR doctrine and KEP `implemented` say freeze; Oxide RFD 1 says discussion continues on `published` and `committed` RFDs may still change; philcalcado keeps an "eternal Feedback Requested" RFC with a revisit date. Recorded, not resolved. (Sources 7, 25, and the Fowler bliki https://www.martinfowler.com/bliki/ArchitectureDecisionRecord.html.)
2. **Mandatory AI-authorship disclosure vs accountable ownership instead.** philcalcado argues disclosure becomes less useful as AI authoring normalizes, trading provenance for defensibility — opposing the provenance direction implied by other agent-era work.
3. **Minimum viable proposal size.** eric.lubow: five things is enough; "if it takes longer to document the change than it would to code it, you're over-indexing". Spotify Heroic: three sections. HashiCorp: background ≤2 paragraphs, proposal 1, implementation "a couple of pages". philcalcado: hard word budget *plus* mandatory diagrams, traceable claims and a rubric. IETF published RFC: ~15 required elements. No agreement; the apparent rule is that document weight tracks blast radius and gate strictness.
4. **I-D boilerplate says "six months" while operative expiry is 185 days.** Both are current IETF-published text (sources 2 and 3). [interpretation] Likely frozen legacy boilerplate vs. implemented rule; I found no authoritative reconciliation. Recorded as an open discrepancy.
5. **FCP unanimity vs speed.** Rust's maintainers and community document both failure modes with no agreed resolution (source 16). Blocking-by-omission vs racing-the-clock.
6. **Whether the review meeting is a gate.** eric.lubow and philcalcado insist it is a milestone/sounding board and the author owns the decision; Squarespace uses a named approver table with "we won't start implementing" without approval; Kubernetes makes PRR approval *blocking*. Direct conflict across published processes.
